# kod 官网后端接口文档

## 1. 说明

- 服务模块：`kod-ai-portal/backend`
- Controller：
  - `com.kod.controller.HealthController`
  - `com.kod.controller.RelayStationController`
  - `com.kod.controller.AuthController`
- 业务服务：
  - `com.kod.service.RelayStationService`
  - `com.kod.service.AuthService`
- 调用方：官网前端 / 管理端 / 联调测试客户端
- baseUrl：`https://kod.kai.com`
- 内部路径：`/api/**`
- 响应包装：业务接口统一 `Result<T>`；健康检查接口直接返回 `Map<String, Object>`
- 数据来源：`relay_station`、`relay_station_key`、`sys_user`

### 1.1 Base URL

| 环境 | baseUrl | 说明 |
| --- | --- | --- |
| 线上 | `https://kod.kai.com` | 对外统一访问地址 |

完整请求地址拼接规则：

```text
{baseUrl} + /api/...
```

示例：

```text
https://kod.kai.com/api/health
```

### 1.2 请求头

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Content-Type: application/json` | POST 接口必填 | JSON 请求体 |
| `Authorization: Bearer <token>` | 获取中转站配置必填 | `POST /api/auth/login` 返回的 JWT |

### 1.3 鉴权规则

| 接口 | 鉴权方式 |
| --- | --- |
| `GET /api/health` | 无 |
| `POST /api/relay-station` | 无 |
| `POST /api/auth/login` | 无 |
| `GET /api/relay-station/config` | JWT Bearer token |

> 说明：当前项目未引入统一安全过滤器，`GET /api/relay-station/config` 在 Controller 内手动读取并解析 `Authorization` 请求头。

### 1.4 统一响应结构

业务接口统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | number | `0` 成功；非 `0` 表示业务失败或系统异常 |
| `message` | string | 响应文案 |
| `data` | object / array / string / number / null | 业务数据，定义见各接口 |

健康检查接口不使用 `Result<T>` 包装，直接返回：

```json
{
  "status": "UP",
  "app": "kod-portal-backend",
  "redis": "UP",
  "timestamp": "2026-07-16T10:30:00"
}
```

### 1.5 接口一览

| 接口 | 鉴权 | 功能 |
| --- | --- | --- |
| `GET /api/health` | 无 | 服务健康检查，附带 Redis 探测状态 |
| `POST /api/relay-station` | 无 | 保存 AI 中转站地址、API Key 和邀请码 |
| `POST /api/auth/login` | 无 | 登录或首次注册，返回 JWT |
| `GET /api/relay-station/config` | JWT | 获取当前用户关联的中转站配置 |

### 1.6 错误码

| code | 含义 | 触发条件 |
| --- | --- | --- |
| `0` | 成功 | 正常返回 |
| `400` | 参数错误 / 业务校验失败 | 必填参数为空、邮箱格式错误、邀请码无效等 |
| `401` | 未授权 / 认证失败 | 密码错误、缺少 token、token 无效或过期、用户不存在 |
| `404` | 资源不存在 | 用户未关联中转站、中转站或 API Key 不存在 |
| `409` | 唯一约束冲突 | 邀请码已存在、邮箱唯一索引冲突等 |
| `500` | 系统异常 | 未被业务异常捕获的服务端异常 |

### 1.7 数据表

| 表 | 说明 | 关键字段 |
| --- | --- | --- |
| `relay_station` | AI 中转站主表 | `id`、`url`、`invite_code` |
| `relay_station_key` | 中转站 API Key 表 | `id`、`station_id`、`api_key` |
| `sys_user` | 用户表 | `id`、`email`、`password`、`station_id` |

关系说明：

- `relay_station.invite_code` 唯一，注册时通过邀请码定位中转站。
- `relay_station_key.station_id` 关联 `relay_station.id`，查询配置时取该中转站最新一条 API Key。
- `sys_user.station_id` 关联用户注册时绑定的中转站。

## 2. 健康检查

### `GET /api/health`

用于探测后端服务状态。接口会尽力探测 Redis 连通性，但 Redis 探测失败不影响 HTTP 200 返回。

#### 请求

无请求参数。

```bash
curl "https://kod.kai.com/api/health"
```

#### 响应

```json
{
  "status": "UP",
  "app": "kod-portal-backend",
  "redis": "UP",
  "timestamp": "2026-07-16T10:30:00"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | string | 服务状态，正常为 `UP` |
| `app` | string | 应用名称，来自 `spring.application.name` |
| `redis` | string | Redis 探测状态，`UP` 或 `DOWN` |
| `timestamp` | string | 服务端当前时间 |

#### 服务侧流程

1. 组装固定服务状态 `status=UP`。
2. 读取应用名称。
3. 调用 Redis `PING` 做尽力探测。
4. 返回当前服务时间。

## 3. 保存 AI 中转站

### `POST /api/relay-station`

保存中转站地址、API Key 和邀请码。中转站地址与邀请码写入 `relay_station`，API Key 写入 `relay_station_key`。

#### 请求

```json
{
  "url": "https://example.com/v1",
  "apiKey": "sk-xxxx",
  "inviteCode": "INVITE-001"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `url` | string | 是 | 中转站地址，例如 `https://example.com/v1` |
| `apiKey` | string | 是 | 中转站 API Key |
| `inviteCode` | string | 是 | 邀请码，唯一 |

请求示例：

```bash
curl -X POST "https://kod.kai.com/api/relay-station" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/v1",
    "apiKey": "sk-xxxx",
    "inviteCode": "INVITE-001"
  }'
```

#### 响应

```json
{
  "code": 0,
  "message": "success",
  "data": 1900000000000000000
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data` | number | 新建中转站主键 ID |

#### 错误码

| code | 含义 | 触发条件 |
| --- | --- | --- |
| `400` | 参数错误 | `url`、`apiKey` 或 `inviteCode` 为空 |
| `409` | 邀请码已存在 | `inviteCode` 已被其他中转站使用 |
| `409` | 唯一约束冲突 | 数据库唯一索引兜底冲突 |
| `500` | 系统异常 | 数据库写入等未预期异常 |

#### 服务侧流程

1. 校验请求体必填字段。
2. 按 `invite_code` 查询是否已存在中转站。
3. 插入 `relay_station`，保存 `url` 和 `invite_code`。
4. 插入 `relay_station_key`，保存 `station_id` 和 `api_key`。
5. 返回新建中转站 ID。

## 4. 登录或首次注册

### `POST /api/auth/login`

同一个接口同时承担登录和首次注册：

- 用户不存在：执行注册，必须传有效 `inviteCode`，注册成功后返回 token。
- 用户已存在：校验密码，`inviteCode` 不生效，可不传。

#### 请求

首次注册：

```json
{
  "email": "user@example.com",
  "password": "pass123",
  "inviteCode": "INVITE-001"
}
```

老用户登录：

```json
{
  "email": "user@example.com",
  "password": "pass123"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `email` | string | 是 | 登录邮箱，必须符合邮箱格式 |
| `password` | string | 是 | 登录密码 |
| `inviteCode` | string | 首次注册必填 | 注册时用于关联中转站；老用户登录不生效 |

请求示例：

```bash
curl -X POST "https://kod.kai.com/api/auth/login" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "pass123",
    "inviteCode": "INVITE-001"
  }'
```

#### 响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9.xxx.yyy",
    "newUser": true
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.token` | string | JWT token，后续认证接口使用 |
| `data.newUser` | boolean | `true` 表示本次新注册；`false` 表示老用户登录 |

#### 错误码

| code | 含义 | 触发条件 |
| --- | --- | --- |
| `400` | 参数错误 | `email` 为空、邮箱格式错误、`password` 为空 |
| `400` | 首次注册缺邀请码 | 新用户未传 `inviteCode` |
| `400` | 邀请码无效 | `inviteCode` 找不到对应中转站 |
| `401` | 邮箱或密码错误 | 老用户登录密码错误 |
| `409` | 唯一约束冲突 | 并发注册导致邮箱唯一索引冲突 |
| `500` | 系统异常 | 数据库写入、JWT 生成等未预期异常 |

#### 服务侧流程

1. 校验 `email` 和 `password`。
2. 按 `email` 查询用户。
3. 用户不存在时，校验 `inviteCode` 并查询中转站。
4. 新用户密码使用 BCrypt 加密，写入 `sys_user`，并绑定 `station_id`。
5. 用户已存在时，使用 BCrypt 校验密码。
6. 生成 JWT，尽力写入 Redis 缓存；Redis 写入失败不影响登录返回。
7. 返回 token 和 `newUser` 标识。

## 5. 获取当前用户关联的中转站配置

### `GET /api/relay-station/config`

根据 JWT 解析当前用户 ID，返回该用户注册时通过邀请码绑定的中转站地址和 API Key。

#### 请求

```bash
curl "https://kod.kai.com/api/relay-station/config" \
  -H "Authorization: Bearer <token>"
```

| Header | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 是 | `Bearer <token>` |

#### 响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "url": "https://example.com/v1",
    "apiKey": "sk-xxxx"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.url` | string | 中转站地址 |
| `data.apiKey` | string | 中转站 API Key |

#### 错误码

| code | 含义 | 触发条件 |
| --- | --- | --- |
| `401` | 缺少或非法的 Authorization 头 | 未传请求头，或格式不是 `Bearer <token>` |
| `401` | token 无效或已过期 | JWT 解析失败或过期 |
| `401` | 用户不存在 | token 中的用户 ID 在 `sys_user` 不存在 |
| `404` | 当前用户未关联中转站 | `sys_user.station_id` 为空 |
| `404` | 关联的中转站不存在 | `relay_station` 中找不到绑定记录 |
| `404` | 中转站未配置 API 密钥 | `relay_station_key` 中找不到关联密钥 |
| `500` | 系统异常 | 数据库查询等未预期异常 |

#### 服务侧流程

1. 校验 `Authorization` 请求头格式。
2. 从 Bearer token 中截取 JWT。
3. 解析 JWT `subject` 得到用户 ID。
4. 查询用户及其 `station_id`。
5. 查询关联中转站。
6. 查询该中转站最新一条 API Key。
7. 返回 `url` 和 `apiKey`。

## 6. 联调流程

### 6.1 完整调用链

1. 创建中转站：

```bash
curl -X POST "https://kod.kai.com/api/relay-station" \
  -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/v1","apiKey":"sk-xxxx","inviteCode":"INVITE-001"}'
```

2. 使用邀请码首次登录，自动注册并获取 token：

```bash
curl -X POST "https://kod.kai.com/api/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"pass123","inviteCode":"INVITE-001"}'
```

3. 使用 token 获取中转站配置：

```bash
curl "https://kod.kai.com/api/relay-station/config" \
  -H "Authorization: Bearer <token>"
```

### 6.2 HTTP Client 测试文件

可使用以下测试文件按顺序执行：

```text
kod-ai-portal/openspec/http/kod-portal-api.http
```

重复执行时，`POST /api/relay-station` 可能返回 `409`，因为 `inviteCode` 具有唯一约束；这是正常结果，可更换测试邀请码后重试。
